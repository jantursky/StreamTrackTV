The app targets Android 8.0 (API 26) and newer and is built for the remote. It starts in the dark theme and has a light theme in Settings.

## Onboarding

On first start the app asks for the server address, then shows a 6-character code and a QR code that points to `{server}/pair?code=`. Confirm it in the dashboard. The device token is stored encrypted with a key from the Android Keystore. After pairing, the **Setup** screen lists the permissions.

## Permissions

| Permission                                | Why                                | What it gives the app                      |
| ----------------------------------------- | ---------------------------------- | ------------------------------------------ |
| Usage access                              | Read app usage events from Android | Foreground time per app and screen-on time |
| Accessibility service                     | Receive remote key events          | The class of each key press                |
| Battery optimization exemption (optional) | Keep syncing in standby            | Nothing extra to read                      |
| Internet                                  | Send totals to your server         | Nothing extra to read                      |

### Granting permissions with adb

Some TVs hide the settings pages. The app then shows the matching command, and you can run them yourself:

```bash
PKG=com.jantursky.streamtracktv

# Usage access
adb shell appops set $PKG GET_USAGE_STATS allow

# Accessibility service. This replaces the list of enabled services.
# If others are enabled, read the list first and append ours with a colon.
adb shell settings get secure enabled_accessibility_services
adb shell settings put secure enabled_accessibility_services $PKG/com.jantursky.streamtracktv.collector.KeyPressService

# Battery optimization exemption
adb shell dumpsys deviceidle whitelist +$PKG
```

## What the accessibility service sees

Accessibility is a powerful permission, and Android warns about it for a reason. This service only counts key presses. It cannot read window content and receives no accessibility events. The code turns each key press into a class and discards the key code. Counts are held in memory and added to the local database every minute.

The classes are `dpad`, `select`, `back`, `home`, `media`, `volume` and `other`. Text typed with an on-screen keyboard is not read.

## What is never collected

- Which key was pressed beyond its class.
- Typed text, screen content, window titles or screenshots.
- What is watched inside an app.
- Location, microphone, camera, contacts, accounts or advertising IDs.

Package names, app display names and durations are the most specific data that leaves the TV. App data is excluded from cloud backup and device transfer. See [privacy and security](/privacy-and-security).

## Screens

- **Dashboard.** Today's summary, top apps and keypresses on the TV.
- **History.** Past days from the data on the TV. See [History](#history).
- **Privacy.** The exact JSON of the next upload, and the security events waiting to go with it.
- **Setup.** The permission checklist described above.
- **Settings.** Sync interval (15 minutes to 24 hours), a daily screen time limit, per-app limits, excluded apps, light or dark theme, the server address, unpairing and deleting local data.

## History

The History tab reads the hourly data already stored on the TV, so it needs no extra permission and sends nothing. Choose a quick period (**Today**, **Yesterday**, **This week**, **Last week**, **This month** or **Last month**) or a rolling **Day**, **7 days** or **30 days**. Weeks start on the first day of the week of the TV's language, and a period that has not ended stops at today. **Previous** and **Next** move one day, or one whole week or month for a quick period, never past today, and **Today** jumps back. Under the totals, a comparison shows how screen time, app time and remote presses differ from the period just before (the same weekdays of the week before, for a week in progress); it is left out when that period has no data. A **Highlights** card gives the daily average over days with data, the busiest day and the peak hour. The day view draws one bar per hour, with screen-on time behind and app time in front. The longer views draw one bar per day and list every day below the chart; select a day to open it. Select an app in the list to narrow app time to it, and select it again, or choose **Show all apps**, to clear the filter. Screen-on time and remote presses are not per app, so the filter leaves them as they are. Remote presses are listed by key class only, and apps excluded in Settings never appear.

## PIN lock and security log

**Settings → PIN lock** asks for a 4 to 8 digit PIN, entered on a keypad that works with the D-pad. The app asks for it on every start and whenever it comes back from the background. Three wrong tries are free; after that the keypad waits 30 seconds, then longer, up to 15 minutes. **Forgot PIN** shows a code and a QR code; confirm it on the dashboard at `/pin-reset` with the account that owns the TV and the TV clears the PIN.

The app records when it is opened and what happens at the lock (see [privacy and security](/privacy-and-security#security-events)), keeps the newest 500 events and sends new ones with each sync. They show up on the dashboard's Security page. The PIN itself is never recorded.

## Excluding an app

In Settings, Apps, you can exclude an app. It is neither recorded nor uploaded from then on, and its stored hours on the TV are deleted. Data already uploaded stays on the server. Delete it from the dashboard if you want it gone.

## Data on the device

The app keeps hourly buckets in a local database, with absolute values per hour. A row whose value changes is marked unsent. The sync worker sends unsent rows in batches of at most 2000 rows per kind and 900 KiB of JSON, and marks exactly the sent values as sent. A repeated upload changes nothing, because the server stores absolute values. A `401` removes the token and returns the app to pairing. A `429` with `Retry-After` schedules one more sync after that delay. Without it, and on `5xx` and network errors, the worker retries with exponential backoff. A `400` or `413` halves the batch and tries again. A single row that is still refused is set aside, counted on the Privacy screen, and sent again only if its value changes. Other `4xx` responses stop the run.

Usage events carry no record of a power loss. When the TV boots, or the screen turns on while it was already on, the open app session and screen-on interval end at the last event seen before. A TV that lost power is therefore not counted as on until the next boot.

Pairing polls every 5 seconds and waits out a `Retry-After`. A code's lifetime is measured on the TV's clock from the moment it arrived. After six unclaimed codes the TV stops asking and waits for you.

## Debug builds

Debug builds have **Settings, Load demo week**, which replaces local data with a generated week, and they accept a plain `http://` server on the local network. Release builds have neither.
